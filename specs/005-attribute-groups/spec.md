# Feature Specification: Attribute Management – Attribute Groups (Administración de Atributos – Grupos de Atributos)

**Feature Branch**: `005-attribute-groups`

**Created**: 2026-11-09

**Status**: Approved

**Approved**: 2026-11-09, by the project owner, together with the plan's decisions D-1 to D-9
(plan.md), with D-1 changed to MongoDB storage (constitution 2.3.0, ADR 0003)

**Input**: User request of 2026-11-09 (referred to below as *the feature request*): "create another
feature to manage the group attributes for the user", after reviewing how attribute grouping works in
`ERF 1.1 Plantillas.docx` §3.2 ¶3 and §3.2.2. Builds on feature 004, whose attributes are created
without groups (feature 004 FR-017: "linking … is deferred to a future attribute group feature, which
must also let existing attributes be linked").

## Context

The ERF asks that attributes be linked to one or more **attribute groups**, which "facilitará su
organización visual en las interfaces de usuario (UI) y su comportamiento en las exportaciones"
[Source: p360:ERF - HUs/ERF 1.1 Plantillas.docx §3.2 ¶3]. §3.2.2 adds that administrators create groups
as they need them, that an attribute may belong to several groups, and that an attribute can leave a
group without being deleted [§3.2.2, "Algunas consideraciones"].

§3.2.2 also says that whatever is attached to a group spreads to its attributes: an object linked to a
group inherits the group's attributes, and a behaviour or metadata value set on a group applies to all
its attributes. None of those targets exist yet in pim-platform (no templates, no exports, no
attribute metadata), so this feature delivers **the groups themselves and their membership**, and
records the inheritance rules as dependencies for the features that will add those targets.

### What a group is, in this feature

- A named set of attributes, managed by an authorized user.
- An attribute may be in any number of groups, including none (feature 004 creates ungrouped
  attributes).
- Adding an attribute to a group or removing it never changes or deletes the attribute itself.

## Clarifications

### Session 2026-11-09

- Q: Can an attribute group contain other groups, or are all groups at the same level? → A: **Flat:
  groups cannot contain groups**; subgroups such as "Logísticos" are ordinary groups of their own
  (OQ-001, Option A). FR-004, the edge cases and Key Entities were updated.
- Q: Can a group be renamed or deleted after it is created, and what happens to a group that still has
  attributes? → A: **A group can be renamed and its description edited; only an empty group can be
  deleted** — deleting a group that still has attributes is refused with a message (OQ-002,
  Option B). FR-005, new User Story 5, the edge cases and Success Criteria were updated.
- Q: Which permission should be needed to create, rename and delete groups and to change their
  attributes? → A: **The same `ATTRIBUTE_CREATE` permission as feature 004** (OQ-003, Option B):
  managing groups changes the global attribute structure (§3.2 ¶1), which feature 004 already gives to
  that permission (its decision D-2). FR-002, the user description, DEP-02 and CF-001 were updated.
- Q: Should the system start with the groups §3.2.2 names as examples already created, or with no
  groups? → A: **Start empty; administrators create the groups they need** (OQ-004, Option A). The
  §3.2.2 groups are examples, not a predefined catalogue. New FR-015 and A-005 were updated.
- Q: Should groups get a system ID from feature 003, or a simpler internal identifier of their own? →
  A: **An internal identifier generated by the group feature; no feature 003 ID** (OQ-006, Option A).
  Attribute groups are not among the six object types of ERF §3.1, and feature 003's behaviour is not
  changed (its storage moves to MongoDB under D-1, ADR 0003). New FR-016, DEP-07 and Key Entities were
  updated.

## User Scenarios & Testing *(mandatory)*

The user is an **authorized user**: a user holding the `ATTRIBUTE_CREATE` permission, the same one
that creates attributes in feature 004 (FR-002). The source calls this person "el usuario administrador" [§3.2.2]; no role is fixed here
(CF-001).

### User Story 1 - Create an attribute group (Priority: P1)

An authorized user creates a group by giving it a name (and optionally a description), so attributes
can be organized under it.

**Why this priority**: Without groups nothing else in this feature works. §3.2.2: «el usuario
administrador debe tener la oportunidad de poder crear "Grupos" según requiera».

**Independent Test**: Create a group "Logísticos"; it appears in the list of groups with no
attributes. A user without the permission cannot create it.

**Acceptance Scenarios**:

1. **Given** an authorized user, **When** they enter the name "Logísticos" and save, **Then** the
   group is created with no attributes and a Spanish confirmation is shown.
2. **Given** a group "Logísticos" exists, **When** a group named " logísticos " is created, **Then**
   it is refused because the name is already used (A-002).
3. **Given** an empty or blank name, **When** the user saves, **Then** saving is refused and the page
   says the name is required.
4. **Given** a user without the permission, **When** they try to create a group, **Then** it is
   refused with an explanatory message and nothing is saved.

---

### User Story 2 - Add attributes to a group (Priority: P1)

An authorized user adds one or more existing attributes to a group. The same attribute can be added
to several groups.

**Why this priority**: This is the link §3.2 ¶3 requires («Los atributos deben vincularse a uno o
varios Grupos de Atributos») and that feature 004 deferred.

**Independent Test**: With attributes "Peso" and "Volumen" created by feature 004, add both to
"Logísticos" and "Peso" also to "Compra Ventas"; each group lists its attributes, and "Peso" shows
both groups.

**Acceptance Scenarios**:

1. **Given** the group "Logísticos" and the attributes "Peso" and "Volumen", **When** the user adds
   both, **Then** the group lists "Peso" and "Volumen".
2. **Given** "Peso" is in "Logísticos", **When** the user also adds it to "Compra Ventas", **Then**
   "Peso" belongs to both groups («Un Atributo puede pertenecer en más de un grupo», §3.2.2).
3. **Given** "Peso" is already in "Logísticos", **When** the user adds it again, **Then** the group
   still lists it once, and the user is told it was already there.
4. **Given** an attribute or group that does not exist, **When** the user tries to link them, **Then**
   the request is refused with a message naming what was not found.
5. **Given** an attribute is added to a group, **When** the attribute is read, **Then** its own data
   (name, type, properties, system ID) is unchanged.

---

### User Story 3 - Remove an attribute from a group (Priority: P1)

An authorized user removes an attribute from a group. The attribute stays in the system and in its
other groups.

**Why this priority**: Explicit in §3.2.2: «Un atributo debe poder desvincularse del grupo, sin ser
eliminado del sistema».

**Independent Test**: Remove "Peso" from "Logísticos"; "Logísticos" no longer lists it, "Peso" still
exists and is still in "Compra Ventas".

**Acceptance Scenarios**:

1. **Given** "Peso" is in "Logísticos" and "Compra Ventas", **When** the user removes it from
   "Logísticos", **Then** "Logísticos" no longer lists it, "Peso" still exists, and it is still in
   "Compra Ventas".
2. **Given** "Peso" is only in "Logísticos", **When** the user removes it, **Then** "Peso" still
   exists with no groups (A-003).
3. **Given** an attribute that is not in the group, **When** the user tries to remove it, **Then** the
   user is told it was not in the group, and nothing changes.

---

### User Story 4 - See groups and their attributes (Priority: P2)

Any user of the application can see the list of groups, the attributes of a group, and the groups an
attribute belongs to.

**Why this priority**: Needed to manage groups, and it is the "organización visual" of §3.2 ¶3 at its
simplest. Showing groups as sections of product screens comes with product features.

**Independent Test**: The list shows "Logísticos" (2 attributes) and "Compra Ventas" (1 attribute);
opening "Logísticos" lists "Peso" and "Volumen"; the attribute "Peso" lists both groups.

**Acceptance Scenarios**:

1. **Given** groups exist, **When** the user opens the groups page, **Then** every group is listed
   with its name, description and number of attributes.
2. **Given** a group, **When** the user opens it, **Then** its attributes are listed with their display
   name, data type and system ID.
3. **Given** an attribute, **When** its groups are requested, **Then** every group it belongs to is
   listed.
4. **Given** no group exists yet, **When** the user opens the groups page, **Then** it says there are
   no groups yet and, for an authorized user, offers to create one.

---

### User Story 5 - Rename or delete a group (Priority: P3)

An authorized user corrects a group's name or description, and deletes a group that is no longer
needed once it has no attributes.

**Why this priority**: Housekeeping for groups created in User Story 1; not stated in §3.2.2 but
settled in clarification 2026-11-09 (FR-005).

**Independent Test**: Rename "Logisticos" to "Logísticos"; the group keeps its attributes. Deleting it
while it has attributes is refused; after removing them, deleting it succeeds and the attributes still
exist.

**Acceptance Scenarios**:

1. **Given** a group with attributes, **When** an authorized user changes its name or description,
   **Then** the change is saved and the group keeps all its attributes.
2. **Given** another group is named "Compra Ventas", **When** a group is renamed to " compra ventas ",
   **Then** the rename is refused because the name is already used (FR-003).
3. **Given** a group that still has attributes, **When** the user tries to delete it, **Then** the
   deletion is refused with a message saying the group must be emptied first, and nothing changes.
4. **Given** an empty group, **When** the user deletes it, **Then** it no longer appears in the list.
5. **Given** a user without the permission, **When** they try to rename or delete a group, **Then** it
   is refused and nothing changes.

---

### Edge Cases

- **Group name differing only in letter case or surrounding spaces from an existing one**: refused as
  a duplicate (A-002).
- **Very long name or description**: limits are not stated (OQ-007).
- **Adding the same attribute twice to one group**: no duplicate membership; the user is told
  (US2 scenario 3).
- **Removing the last group of an attribute**: allowed; the attribute stays ungrouped (A-003, OQ-005).
- **An attribute in two groups that later get conflicting settings** (behaviour or metadata, §3.2.2
  rules 5–6): not possible in this feature, which has no group settings; recorded for the features
  that add them (OQ-008).
- **Group inside a group** (e.g. "Atributos Maestros" containing "Datos Básicos"): not possible;
  groups are flat (FR-004).
- **Renaming a group** that has attributes: allowed; memberships are kept (FR-005).
- **Deleting a group** that has attributes: refused until it is empty; an empty group can be deleted
  (FR-005).
- **Attribute list-of-values or other types**: membership works the same for every data type.
- **The system cannot store the change**: Spanish error, nothing half-done (A-006).

## Requirements *(mandatory)*

### Explicit Requirements

Sources: the feature request and `p360:ERF - HUs/ERF 1.1 Plantillas.docx`, cited as [3.2 ¶3] and
[3.2.2 rule n] (n = the bullet under "Algunas consideraciones": 1 = admins create groups, 2 = an
attribute in several groups, 3 = an object linked to a group inherits its attributes, 4 = behaviours
on a group apply to its attributes, 5 = metadata on a group applies to its attributes, 6 = an attribute
leaves a group without being deleted). No tier 1 document in `docs/source-of-truth/` covers this
feature.

**Groups**

- **FR-001**: An authorized user MUST be able to create an attribute group with a **name** and an
  optional **description**. [3.2.2 rule 1]
- **FR-002**: Creating, renaming and deleting groups and changing their membership MUST require the
  **`ATTRIBUTE_CREATE`** permission, the same one feature 004 uses for creating attributes and
  affecting the global attribute structure. A user without it MUST be refused with an explanatory
  Spanish message, and nothing MAY change. Seeing groups needs no permission (A-004). [3.2.2 rule 1;
  3.2 ¶1 «Solo perfiles autorizados … podrán afectar la estructura global»; clarification 2026-11-09
  (OQ-003)]
- **FR-003**: Group names MUST be unique, compared ignoring letter case and surrounding spaces.
  [A-002, to confirm]
- **FR-004**: Groups MUST be **flat**: a group contains attributes only, never other groups. The
  subdivisions §3.2.2 names under "Atributos Maestros" ("Datos Básicos", "Logísticos", "Compra
  Ventas") are ordinary groups of their own. [3.2.2 examples; clarification 2026-11-09 (OQ-001)]
- **FR-005**: An authorized user MUST be able to **rename** a group (subject to FR-003) and **change
  its description**; its memberships MUST be kept. A group MUST be **deletable only when it has no
  attributes**; deleting a group that still has attributes MUST be refused with a Spanish message
  saying it must be emptied first, and nothing MAY change. [Clarification 2026-11-09 (OQ-002);
  §3.2.2 only speaks of creating groups]
- **FR-015**: The system MUST start with **no groups**. The groups §3.2.2 lists (Atributos Maestros,
  Datos Básicos, Logísticos, Compra Ventas, Características, ATG, MKP, Conjunto Look, Sistema) are
  examples and MUST NOT be pre-created. [3.2.2 rule 1 «según requiera»; clarification 2026-11-09
  (OQ-004); CF-003]

- **FR-016**: Each group MUST have an **identifier generated by the system** when it is created, which
  never changes, even when the group is renamed. Groups do NOT receive a system ID from feature 003
  (attribute groups are not among the six object types of ERF §3.1), and feature 003's behaviour is not
  changed; only its storage moves to MongoDB (D-1, ADR 0003, feature 003 amendment).
  [Clarification 2026-11-09 (OQ-006)]

**Membership**

- **FR-006**: An authorized user MUST be able to add one or more existing attributes (feature 004) to
  a group. [3.2 ¶3]
- **FR-007**: An attribute MAY belong to more than one group, and to none. [3.2.2 rule 2; feature 004
  FR-017; A-003]
- **FR-008**: An attribute MUST appear at most once in a group; adding it again MUST leave the group
  unchanged and tell the user. [Derived from FR-006]
- **FR-009**: An authorized user MUST be able to remove an attribute from a group; the attribute MUST
  stay in the system, unchanged, and in its other groups. [3.2.2 rule 6]
- **FR-010**: Adding an attribute to a group or removing it MUST NOT change any data of the attribute
  itself (display name, data type, properties, system ID). [3.2.2 rule 6; feature 004]
- **FR-011**: A request naming a group or attribute that does not exist MUST be refused with a Spanish
  message naming it, and nothing MAY change.

**Viewing**

- **FR-012**: The application MUST list the groups with name, description and number of attributes;
  list the attributes of a group (display name, data type, system ID); and list the groups of an
  attribute. [3.2 ¶3 "organización visual"]
- **FR-013**: The groups page MUST use the existing design system, be reachable from the side
  navigation, and get every group and attribute from the backend through its REST API; the frontend
  MUST hold no group or attribute data. [Feature request; constitution III; feature 004 FR-022]

**Deferred (recorded, not built here)**

- **FR-014**: Linking a group to an object (for example a template) so the object inherits the group's
  attributes [3.2.2 rule 3], attaching a behaviour such as an export to a group [rule 4], and setting
  metadata on a group [rule 5] are NOT part of this feature. The features that introduce templates,
  exports and attribute metadata MUST apply these rules to the groups created here (DEP-03 to
  DEP-05).

### Observed Existing Behavior

From the reference repository's analysis (tier 2 analysis of tier 3 evidence); not requirements.

- **OEB-001**: P360 has seven different mechanisms called "group" today: a portal section, a display
  group, a characteristic category, a STEP group with permissions P360 does not apply, an ATG
  grouping, an SAP group per attribute and relevance per channel. [Evidence (as summarized):
  p360:P360-repositorios/nuevo-pim/docs/arquitectura/pim-headless/dudas.md:306-310 (DUD-16, H-T10)]
- **OEB-002**: P360 holds 125 attribute groups inherited from STEP (catalog `AttributeGroup`, about
  23 K references). [p360:…/pim-headless/modulos/01-plantillas.md:213]

### Conflicts and Open Decisions in Related Documents

Reported per constitution XI; not used as requirements.

- **CF-001 – Who manages groups**: §3.2.2 says "el usuario administrador"; §3.2 ¶1 gives
  "Administrador de Catálogo" as the profile that changes the global structure; the Templates HU uses
  "Manager" and `PIM_Catalog_Admin` (feature 004 CF-001). This spec reuses `ATTRIBUTE_CREATE` and fixes no role (FR-002).
- **CF-002 – "Must be linked" versus "may be unlinked"**: §3.2 ¶3 says attributes «deben vincularse a
  uno o varios Grupos», which suggests at least one group; §3.2.2 rule 6 allows leaving a group, and
  feature 004 creates ungrouped attributes. (OQ-005)
- **CF-003 – Group taxonomy undecided**: the reference repository records the new PIM's group
  taxonomy as an open business decision (choose among the seven current mechanisms or define a new
  one), with a proposal that today's groups migrate as "types".
  [p360:…/pim-headless/decisiones.md:186 (PD-14); dudas.md:306 (DUD-16)] (OQ-004)

### Key Entities

- **Attribute group**: identifier generated by the system (FR-016), name (unique, ignoring case), optional description, its member attributes.
  No parent group: groups are flat (FR-004).
- **Membership**: the link between one attribute and one group; at most one per pair.
- **Attribute** (feature 004; its data and rules are not changed here, only its storage moves to
  MongoDB, and a read-only list of attributes is added, plan D-3): what is grouped.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An authorized user can create a group and add three attributes to it in under 1 minute.
- **SC-002**: 100% of membership changes leave the attribute's own data unchanged and the attribute
  still present in the system.
- **SC-003**: 100% of attempts by users without the permission are refused, and nothing changes.
- **SC-004**: An attribute in N groups is listed by each of those N groups, and its group list shows
  exactly those N groups.
- **SC-005**: 100% of duplicate group names (ignoring letter case and surrounding spaces) and of
  duplicate memberships are refused or reported, with no second group or membership created.
- **SC-006**: In a walkthrough, at least 4 of 5 authorized users create a group and move an attribute
  between two groups on their first attempt, without help.
- **SC-007**: 100% of attempts to delete a group that still has attributes are refused, and after a
  rename the group keeps 100% of its attributes.

## Assumptions

- **A-001**: Groups are managed one at a time from a page of the application; bulk loads of groups are
  out of scope.
- **A-002**: Group names are unique ignoring letter case and surrounding spaces, like attribute display
  names in feature 004 (FR-023 there). Not stated in the source; to confirm.
- **A-003**: An attribute may be in no group, because feature 004 creates attributes without groups
  and §3.2.2 allows leaving a group (CF-002, OQ-005).
- **A-004**: Seeing groups (US4) needs no special permission, like reading attributes in feature 004.
- **A-005**: *Confirmed 2026-11-09 and now FR-015:* no groups exist when the feature starts.
- **A-006**: Errors follow features 001–004: Spanish messages, nothing half-saved, the user can retry.

## Out of Scope

- Linking groups to templates or other objects, and inheritance of attributes through groups
  (§3.2.2 rule 3, FR-014).
- Behaviours (exports, outputs) and metadata on groups (§3.2.2 rules 4–5, FR-014).
- Choosing groups inside the attribute creation form of feature 004 (OQ-009).
- Permissions per group (who may edit the attributes of a group), audit history of group changes.
- Bulk import of groups or memberships; migration of P360's groups (OEB-002).
- Ordering of groups or of attributes inside a group on product screens (template metadata, §3.3).
- Editing or deleting attributes (feature 004 out of scope).

## Open Questions

None of the remaining open questions blocks planning; each must be answered or recorded as a
decision in the plan.

- **OQ-001**: *Resolved 2026-11-09: flat groups only (FR-004).* Can a group **contain other groups** (e.g. "Atributos Maestros" → "Datos
  Básicos", "Logísticos", "Compra Ventas")? If so, how many levels, and is an attribute of a subgroup
  also a member of the parent? (FR-004)
- **OQ-002**: *Resolved 2026-11-09: rename and edit allowed; only empty groups can be deleted
  (FR-005).* May a group be **renamed** or have its description changed, and may it be
  **deleted**? If deleted, are its memberships simply removed (the attributes stay), or is deleting a
  non-empty group refused? (FR-005)
- **OQ-003**: *Resolved 2026-11-09: `ATTRIBUTE_CREATE`, as in feature 004 (FR-002).* Which **permission** manages groups: the same `ATTRIBUTE_CREATE` as feature
  004, or a separate one (for example `ATTRIBUTE_GROUP_MANAGE`)? (FR-002, CF-001)
- **OQ-004**: *Resolved 2026-11-09: start empty (FR-015).* Should the system start with the **groups named in §3.2.2** (Atributos Maestros, Datos
  Básicos, Logísticos, Compra Ventas, Características, ATG, MKP, Conjunto Look, Sistema), or empty?
  The group taxonomy is an open business decision (CF-003, PD-14).
- **OQ-005**: Must every attribute belong to **at least one group** eventually (§3.2 ¶3 «deben
  vincularse»), or may attributes stay ungrouped (CF-002)?
- **OQ-006**: *Resolved 2026-11-09: internal identifier, no feature 003 ID (FR-016).* Do groups need a **system ID** under feature 003's rules (they are not among its six
  object types), or are they identified another way?
- **OQ-007**: What are the **limits** for group name and description (length, allowed characters)?
- **OQ-008**: When group settings arrive (behaviours, metadata), how are **conflicts** resolved for an
  attribute in two groups with opposite settings, and does a group setting override the attribute's
  own value? (For the features that add them; recorded here so it is not lost.)
- **OQ-009**: Once groups exist, should feature 004's **creation form** let the user choose groups
  (§3.2 ¶3 speaks of linking attributes, not of when)? That would amend feature 004.
