# Data Model: Attribute Inheritance through the Product Taxonomy

**Feature**: `010-taxonomy-attribute-inheritance` | **Plan**: [plan.md](plan.md)

## Stored: `taxonomy_nodes` (MongoDB, owner domain `taxonomy`)

Requires constitution 2.5.0 (Principle IX) and the ADR 0003 amendment (plan D-2).

| Field | Type | Rules |
|---|---|---|
| `_id` | string | System ID upper-cased (lookups ignore letter case) |
| `systemId` | string | Generated by feature 003, object type `CLASSIFICATION` (`CLS000001`…); never changes (FR-002) |
| `name` | string | Trimmed, 1–80 characters (FR-004, A-006) |
| `nameKey` | string | `name` trimmed and lower-cased; unique among siblings |
| `parentId` | string \| null | Parent's `_id`; `null` for a top-level node; set at creation, never changed (FR-005) |
| `description` | string \| null | Trimmed, ≤ 500 characters; blank → `null` |
| `attributeIds` | string[] | Direct attribute system IDs, upper-cased, in assignment order, no duplicates (FR-009) |
| `createdAt` | date | Set at creation |
| `updatedAt` | date \| null | Set on rename, description change or assignment change |

**Indexes**: `_id`; unique `taxonomy_node_sibling_name_unique` on `{ parentId: 1, nameKey: 1 }`;
`taxonomy_node_attribute_ids` on `{ attributeIds: 1 }` (deletion check, FR-021).

**Invariants** (service, under the taxonomy lock):
- the parent exists when a node is created; a node with children is never deleted (no orphans);
- a node with direct attributes is never deleted;
- every `attributeIds` entry names an existing attribute when added; attribute deletion is refused
  while any node lists it (FR-021), so entries never dangle;
- no cycles: the parent is fixed at creation and must already exist.

| Type | Shape | Notes |
|---|---|---|

| `TaxonomyNode` | systemId, name, description, parentId (Optional), attributeIds (List), createdAt, updatedAt (Optional) | Immutable; `renamed(…)`, `withAttributes(…)`, `withoutAttribute(…)` return copies |
| `NodeReference` | systemId, name | Used in path, children, origins |
| `AssignmentType` | `DIRECT`, `INHERITED` | |
| `EffectiveAttribute` | attributeId, assignment, origin (`NodeReference`), alsoInheritedFrom (Optional `NodeReference`) | Before attribute names are resolved |
| `EffectiveAttributes` | `static List<EffectiveAttribute> of(TaxonomyNode, Map<String, TaxonomyNode>)` | Pure; rules below |
| `NodeDetails` | node, level, path, children, effective attributes with display name and data type | What the service returns to the controller |
| `AddAttributesOutcome` | details, added, alreadyAssigned | |

### `EffectiveAttributes` rules (FR-012 to FR-016)

1. Chain = ancestors from the top level down, then the node.
2. For each chain node in that order, for each of its `attributeIds` in order: the attribute's origin
   becomes this node (the nearest one wins); a previous origin is kept as "also inherited from"
   candidate.
3. `assignment` = `DIRECT` when the final origin is the node itself, else `INHERITED`.
4. `alsoInheritedFrom` = for `DIRECT` entries only, the nearest ancestor that also has the attribute
   directly.
5. Order: `INHERITED` entries by origin depth ascending, then by position in the origin's list;
   then `DIRECT` entries in the node's list order.
6. Level = chain length; path = chain without the node.

Example (feature request): `Camisas` → Color, Material, Marca (INHERITED, origin Ropa), Género
(INHERITED, origin Ropa de hombre), Largo de manga (DIRECT, origin Camisas).
