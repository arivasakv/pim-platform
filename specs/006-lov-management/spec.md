# Feature Specification: List of Values Management (Administración de Listas de Valores – LOV)

**Feature Branch**: `006-lov-management`

**Created**: 2026-11-11

**Status**: Approved

**Approved**: 2026-11-11, by the project owner, together with the plan's decisions D-1 to D-12
(plan.md); remaining assumptions (A-002, A-004–A-006, A-008) accepted as recorded

**Input**: User request of 2026-11-11 (referred to below as *the feature request*): create a feature
"LOV Management (List of Values)" so that authorized users can manage reusable lists of values, their
values, their links to attributes, and the operations that maintain or migrate the values products
use. Requirements source: `ERF 1.1 Plantillas.docx` §3.2.1 "Tipos de Atributos" (LOV rules), with
related sections used only to understand dependencies. Builds on feature 004, whose LOV attributes
cannot be saved until lists exist (feature 004 FR-012, DEP-03).

## Context

§3.2.1 defines lists of values (LOVs) as «Listados predefinidos para estandarizar la captura», of
single or multiple selection, made of ID–label pairs, reusable by several attributes, and maintained
manually or in bulk [Source: p360:ERF - HUs/ERF 1.1 Plantillas.docx §3.2.1 "Listas de Valores"].
The same section asks for operations that change the values **products** hold: label changes
propagated to every product, value deletion with a count of affected records, migration of products
from one value to another, merge of two values, and migration of products between attributes.

Today pim-platform has:

- **Attribute creation** (feature 004), including the "Lista de valores" type with a selection mode
  and a link to an existing list. No list exists, so those attributes cannot be saved yet.
- **System IDs** (feature 003), where "lista de valores" is already one of the six object types.
- **Attribute groups** (feature 005).
- **A product catalog** (feature 002) that holds only SKU, EAN, title, brand and business. Products
  hold **no attribute values** yet, and no feature captures them.
- **No attribute editing**: feature 004 fixes an attribute's type at creation.

### Scope of this feature

Decided on 2026-11-11 (see [Clarifications](#clarifications)): this feature delivers **lists, their
values (manual and bulk), equivalences, and the view of which attributes use each list**. The §3.2.1
rules that need product values, attribute editing, or two attributes at once go to follow-up
features (see [Follow-up Features](#follow-up-features)):

| §3.2.1 rule | Where |
|---|---|
| ID–label pairs, numeric or alphanumeric IDs, unique within a list | This feature |
| Manual and bulk administration, external or generated IDs | This feature |
| One list linked to several attributes | This feature (view); linking stays in feature 004 |
| Equivalence column | This feature |
| Value deletion | This feature; the count of affected records and their removal: FU-1 |
| Label change propagated to all products | FU-1 |
| Migrate products between values of one list | FU-1 |
| Merge two values | FU-1 |
| Unlink a list from an attribute, with a new type | FU-2 |
| Migrate products between attributes | FU-3 |

## Clarifications

### Session 2026-11-11

- Q: Products hold no attribute values yet. How should the operations on product values (label
  propagation, usage counts, migration, merge) be delivered? → A: **Split** (OQ-001, Option C): lists,
  values and links now; propagation, usage counts, migration and merge in a later feature (FU-1).
  FR-012, FR-013, FR-017, FR-018, FR-020 to FR-022, User Story 3, DEP-03, the edge cases and the
  success criteria were updated; the migration and merge stories moved to FU-1.
- Q: Unlinking a list changes the attribute's type, but feature 004 has no attribute editing. What
  should this feature do? → A: **Wait for attribute editing** (OQ-003): unlinking is not part of this
  feature and is delivered with or after an attribute-editing feature (FU-2). FR-015, User Story 4
  (now view-only), DEP-04 and OQ-004 were updated.
- Q: Is attribute migration part of this feature? → A: **Separate feature** (OQ-013, FU-3). FR-024
  was updated.
- Q: When a list value comes from an external system, should it have one ID or two? → A: **One ID per
  value** (OQ-007, Option A): typed in (often the external system's code) or generated by the PIM;
  there is no separate external-ID field. FR-009 and Key Entities were updated.
- Q: What is a value's "equivalence"? → A: **One optional free-text equivalence per value** (OQ-008,
  Option A), for mappings to external systems; several values may share the same text; turning the
  column off hides the texts and keeps them. FR-023, User Story 5, CF-003 and FU-3 were updated.
- Q: How should users load many values into a list at once? → A: **CSV file upload with a
  downloadable template** (OQ-005, Option A): columns ID, Etiqueta, Equivalencia; an empty ID means
  "generate one". FR-011 and User Story 4 were updated.
- Q: When a CSV row has an ID that already exists in the list, what should happen? → A: **Update it**
  (OQ-005, Option A; ERF §3.1 "Validación de Duplicidad"): the row's label, and its equivalence when
  given, replace the existing ones; the report shows how many values were added and how many updated.
  FR-008, FR-011, User Story 4, SC-002 and the edge cases were updated.
- Q: Once a value is saved, may its ID be changed? → A: **No** (OQ-006, Option A): the ID cannot be
  changed after saving; only the label and the equivalence can be edited. To use another ID, the user
  deletes the value and adds a new one. FR-010, FR-012 and User Story 3 were updated.

## User Scenarios & Testing *(mandatory)*

The user is an **authorized user**: a user holding the permission to administer lists of values
(FR-002). Other users may consult lists but cannot change them.

### User Story 1 - Create a list of values and capture its values manually (Priority: P1)

The authorized user creates a list (for example "Color"), then adds values one by one, each with an
ID and a label (for example `0001` "Azul", `0002` "Rojo").

**Why this priority**: Without lists, feature 004 cannot save LOV attributes. This story unblocks
that feature and is the smallest useful slice.

**Independent Test**: Create the list "Color" with two values, open it again and see both values;
then create an LOV attribute in feature 004 linked to "Color" and see it saved.

**Acceptance Scenarios**:

1. **Given** an authorized user, **When** they create a list with a valid name, **Then** the list is
   saved with a system ID assigned under feature 003's rules for lists of values, and it has no values.
2. **Given** a list, **When** the user adds a value with ID `0001` and label "Azul", **Then** the
   value is saved and shown in the list.
3. **Given** a list, **When** the user adds a value without giving an ID, **Then** an ID is generated
   that no other value of the list has.
4. **Given** a list with value ID `0001`, **When** the user adds another value with ID `0001`,
   **Then** it is refused with a Spanish message saying that the ID already exists in that list.
5. **Given** two different lists, **When** each gets a value with ID `0001`, **Then** both are saved
   (IDs are unique only within one list).
6. **Given** a user without the permission, **When** they try to create a list or add a value,
   **Then** it is refused and nothing changes.
7. **Given** an attempt to add a value with an empty label, **Then** it is refused with a Spanish
   message naming the missing field.
8. **Given** lists exist, **When** an LOV attribute is created in feature 004, **Then** the existing
   lists are offered and the attribute is saved linked to the chosen one (FR-026).

---

### User Story 2 - Consult lists, their values and their attributes (Priority: P1)

Any user can see all lists, open one, and see its values and the attributes that use it.

**Why this priority**: Users need to see what exists before editing or deleting, and to know which
attributes a change affects.

**Independent Test**: With "Color" linked to two attributes, open "Color" and see its values and
both attributes, each with its name, system ID and selection mode.

**Acceptance Scenarios**:

1. **Given** several lists, **When** the user opens "Listas de valores", **Then** every list is shown
   with its name, system ID, number of values and number of linked attributes.
2. **Given** a list, **When** the user opens it, **Then** its values (ID, label, and equivalence when
   the column is on) and its linked attributes (name, system ID, selection mode) are shown.
3. **Given** a new LOV attribute created in feature 004 with a list, **When** the list is opened,
   **Then** the new attribute appears among its linked attributes.
4. **Given** no lists, **When** the user opens the page, **Then** a Spanish empty-state message is
   shown, with the create action only for authorized users.

---

### User Story 3 - Edit and delete values, rename and delete lists (Priority: P1)

The authorized user changes a value's label, deletes a value after confirming, renames a list, or
deletes a list that no attribute uses.

**Why this priority**: Required by §3.2.1, and the most common maintenance task.

**Independent Test**: Change "Azul" to "AZUL" and see the new label in the list; delete value `0002`
after confirming and see it gone; try to delete a list linked to an attribute and see it refused.

**Acceptance Scenarios**:

1. **Given** value `0001` "Azul", **When** the user changes the label to "AZUL", **Then** the list
   shows "AZUL" with the same ID `0001`.
2. **Given** a value, **When** the user asks to delete it, **Then** a Spanish confirmation is shown,
   and the value is deleted only after confirming; cancelling changes nothing.
3. **Given** a list, **When** the user renames it, **Then** its system ID, values and linked
   attributes are kept.
4. **Given** a list linked to at least one attribute, **When** the user tries to delete it, **Then**
   it is refused with a Spanish message naming how many attributes use it (FR-004).
5. **Given** a list with no linked attribute, **When** the user deletes it and confirms, **Then** the
   list and its values are deleted.
6. **Given** a saved value, **When** the user edits it, **Then** only its label and equivalence can be
   changed; its ID cannot (FR-010).

---

### User Story 4 - Manage values in bulk (Priority: P2)

The authorized user loads many values into a list at once, each with its ID (which may come from an
external system) and label, and sees every error before anything is applied.

**Why this priority**: §3.2.1 requires bulk administration; real lists hold up to tens of thousands
of values (OEB-002).

**Independent Test**: Load 500 values into an empty list; 498 valid and 2 with a repeated ID. See a
report naming the 2 rows and their cause, with nothing applied; fix them, load again, and see all 500.

**Acceptance Scenarios**:

1. **Given** the list page, **When** the user downloads the template, **Then** they get a CSV file
   with the columns ID, Etiqueta and Equivalencia.
2. **Given** a CSV file with valid rows, some with an empty ID, **When** the user uploads it, **Then**
   all values are added in one operation and the empty IDs are generated.
3. **Given** a CSV file with any invalid row (missing label, or the same ID twice in the file),
   **When** it is uploaded, **Then** a report names each wrong row, its column and its cause, and
   **no** value is applied (FR-016).
4. **Given** value `0001` "Azul" in the list, **When** a file with the row `0001;AZUL;` is uploaded,
   **Then** value `0001` gets the label "AZUL" and keeps its equivalence (the cell is empty).
5. **Given** a file that is not a readable CSV or lacks the Etiqueta column, **When** it is uploaded,
   **Then** it is refused with a Spanish message and nothing is applied.
6. **Given** a load, **When** it finishes, **Then** the user sees how many values were added and how
   many were updated.

---

### User Story 5 - Define equivalences for values (Priority: P3)

The authorized user turns on the equivalence column of a list and enters an equivalence for its
values.

**Why this priority**: Optional in §3.2.1 («Se deberá poder activar una columna de equivalencias»).

**Independent Test**: Turn on equivalences for "Color", give "NEGRO INTENSO" the equivalence "NEGRO",
and see it in the list; turn the column off and see it hidden.

**Acceptance Scenarios**:

1. **Given** a list without equivalences, **When** the user turns them on, **Then** each value gets an
   optional equivalence field.
2. **Given** equivalences turned on, **When** the user saves an equivalence for a value, **Then** it is
   shown next to the value.
3. **Given** equivalences with content, **When** the user turns the column off, **Then** the column is
   hidden and the texts are kept; turning it on again shows them unchanged.
4. **Given** two values, **When** both get the equivalence "NEGRO", **Then** both are saved (the same
   text may be shared).

---

### Edge Cases

- **Same label twice in one list** (`0001` "Azul" and `0005` "Azul"): §3.2.1 only forbids repeated
  IDs. Allowed (A-005), pending OQ-011.
- **ID case and spaces**: `abc` and `ABC`, or `0001` and ` 0001 `, in one list. Spaces are trimmed;
  whether case counts follows A-004.
- **Numeric-looking IDs**: `0001` and `1` are different IDs; leading zeros are kept (IDs are text,
  A-003).
- **Deleting the last value of a list**: allowed; the list stays, empty.
- **Deleting a value of a list linked to attributes**: allowed (no product holds values yet); FU-1
  adds the affected-record count and removal from products.
- **Deleting a list linked to attributes**: refused (FR-004). Since unlinking waits for FU-2, such a
  list cannot be deleted until then.
- **A feature 004 attribute linked to a list ID that does not exist** (for example after a failed
  deletion): impossible by FR-004; feature 004 keeps refusing unknown lists.
- **Two users change the same value at once**: the second change is checked against the current
  state; a deleted value can no longer be edited, and a Spanish message says so.
- **A bulk load interrupted part-way**: nothing is applied (FR-016).
- **A bulk row with an existing ID and an empty Etiqueta**: an error (the label is required), not a
  deletion; nothing is applied.
- **A bulk row whose ID matches an existing one only by case or spaces** (` abc` vs `ABC`): treated as
  the same ID, so it updates (A-004).
- **Storage unavailable**: the change is refused with a Spanish "try again" message and nothing is
  partly applied.

## Requirements *(mandatory)*

Requirement IDs are kept stable; requirements moved to follow-up features are marked **Deferred**.

### Explicit Requirements

**Lists**

- **FR-001 – Create and manage lists**: An authorized user MUST be able to create a list of values with
  a name, rename it, and consult it. Every list MUST get a system ID under feature 003's rules for the
  "lista de valores" object type (automatic sequence, optional manual ID with that type's permission,
  global uniqueness, immutability). [§3.2.1; §3.1; feature 003]
- **FR-002 – Permission**: Creating, renaming and deleting lists, and every change to values and
  equivalences, MUST require the permission to administer lists of values. Consulting MUST NOT
  require it. Which permission is used follows OQ-009 (provisionally A-008). [§3.2 ¶1 "Gestión Basada
  en Roles"]
- **FR-003 – List name**: Required; trimmed; unique among lists, ignoring case (A-002, OQ-002).
- **FR-004 – Delete a list**: An authorized user MUST be able to delete a list only when no attribute
  is linked to it; otherwise the deletion MUST be refused with the number of linked attributes (A-006,
  OQ-004). Deleting a list deletes its values.
- **FR-005 – Selection mode**: Single or multiple selection ("Multivalor") MUST be supported. In
  pim-platform the selection mode is a property of each LOV **attribute** (feature 004 FR-012), so one
  list can serve a single-selection attribute and a multiple-selection attribute. The list's detail
  MUST show the selection mode of each linked attribute. (CF-001, OQ-012) [§3.2.1; feature 004 FR-012]

**Values**

- **FR-006 – ID–label pairs**: Each value MUST have an ID and a label, both required. [§3.2.1 «Deben
  manejar pares clave-valor (ID y Etiqueta)»]
- **FR-007 – ID format**: Value IDs MAY be numeric or alphanumeric and MUST be kept as text, preserving
  leading zeros (`0001`). [§3.2.1 «Los IDs pueden ser numéricos o alfanuméricos»; HU2.1 «ej. 0001,
  0002»]
- **FR-008 – ID uniqueness**: Two values of the same list MUST NOT share an ID. The same ID MAY appear
  in different lists. Adding a value manually with an existing ID MUST be refused; in a bulk load the
  existing value is updated instead (FR-011). [§3.2.1 «Dos valores en una Lista de Valor no pueden tener el mismo ID»]
- **FR-009 – Origin of the ID**: When adding a value, the user MUST be able either to enter an ID that
  comes from an external system or to have one generated. The generated ID MUST NOT collide with
  existing IDs of the list. Value IDs are **not** feature 003 system IDs (those are unique across the
  whole system, A-007). A value has **one** ID: when the value comes from an external system, its code
  is entered as the value ID; there is no separate external-ID field (OQ-007). [§3.2.1 «enlazar el
  ID externo proveniente de un sistema externo (en caso de requerirse) o de generar uno de manera
  manual»]
- **FR-010 – Manual management**: An authorized user MUST be able to add, edit and delete values one at
  a time. Editing a value MUST change only its label and equivalence: a value's ID MUST NOT change
  after it is saved (OQ-006). [§3.2.1; HU2.1 "Add Value"]
- **FR-011 – Bulk management**: An authorized user MUST be able to add many values to a list in one
  operation, with the same rules as FR-006 to FR-009, by uploading a CSV file. The page MUST offer a
  downloadable CSV template with the columns ID, Etiqueta and Equivalencia; an empty ID means the ID
  is generated (FR-009); the Equivalencia column is optional. Errors MUST name the row and column
  (FR-016). A row whose ID already exists in the list MUST update that value: its label, and its
  equivalence when the Equivalencia cell is not empty. The same ID twice in one file MUST be reported
  as an error (OQ-005). [§3.1 «utilizará el ID para actualizarlo (siempre y cuando se trate del mismo
  objeto)»; §3.2.1 «El
  PIM debe soportar la administración de LOVs masivamente o de manera manual»]
- **FR-012 – Label change**: An authorized user MUST be able to change a value's label; the value keeps
  its list and ID. A value MUST be identified by its list and ID, never by its label, so that FU-1 can
  show the new label on every product without copying it. **Deferred to FU-1**: the propagation to
  products itself. [§3.2.1 «Si un valor es modificado, debe actualizarse a todos los objetos que lo
  tengan»; HU2.1 "Actualización Automática en Cascada"]
- **FR-013 – Value deletion**: An authorized user MUST be able to delete a value after an explicit
  confirmation. **Deferred to FU-1**: showing the exact number of records that hold the value before
  confirming, and removing it from those records. [§3.2.1 «Notificando que esto generará la
  eliminación en "x" número de registros»; HU2.1 «número exacto X de registros afectados antes de
  confirmar»]

**Links with attributes**

- **FR-014 – Many attributes per list**: A list MAY be linked to any number of attributes; linking
  happens when an LOV attribute is created (feature 004 FR-012). The list's detail MUST show its linked
  attributes (name, system ID, selection mode). [§3.2.1 «Una Lista de Valor puede vincularse a más de
  un atributo»]
- **FR-015 – Unlink**: **Deferred to FU-2** (clarification 2026-11-11). Unlinking a list from an
  attribute, with the attribute given a type other than "Lista de valores" when it is no longer linked
  to any list, is delivered with or after attribute editing. This feature MUST NOT change an
  attribute's type or list. [§3.2.1 «en el caso de la desvinculación debe quedar indicado el tipo de
  atributo diferente a LOV en caso de que ya no se ligue a otra»; HU2.1 «el PIM exigirá redefinir el
  nuevo tipo de dato»]

**Bulk-safety and consistency**

- **FR-016 – All or nothing**: A bulk value load, a value deletion and a list deletion MUST each be
  applied completely or not at all. A bulk load with any invalid row MUST apply nothing and MUST report
  every invalid row and its cause. [HU2.8 "Motor de Validación Previa": «El sistema no aplicará los
  cambios … hasta que todos los errores del reporte hayan sido corregidos»]
- **FR-017 – Confirm before destructive changes**: Deleting a value or a list MUST require explicit
  confirmation; cancelling MUST change nothing. **Deferred to FU-1**: the confirmation for migration
  and merge, and showing the number of products that will change.
- **FR-018 – No inconsistent products**: **Deferred to FU-1**, which MUST ensure that no product holds
  a value that no longer exists, a value from a list not linked to the attribute, or the same value
  twice in a multiple-selection attribute.
- **FR-019 – Audit**: Deleting a value or a list MUST record who did it, when, and the list and values
  involved. FU-1 extends this to migration and merge, with the number of products changed. [§3.2 ¶1
  Data Stewardship] (A-010)

**Operations on product values**

- **FR-020 – Product values**: **Resolved 2026-11-11** (OQ-001, Option C): this feature does not read
  or change product values. FR-012 (propagation), FR-013 (count and removal), FR-017 (migration and
  merge confirmation), FR-018, FR-021 and FR-022 are delivered by FU-1.
- **FR-021 – Migrate products between values of one list**: **Deferred to FU-1**. [§3.2.1 «migrar
  valores de un listado de productos desde un valor de la lista a otro valor de la misma lista»; HU2.1
  "Migración entre Valores de la misma LOV"]
- **FR-022 – Merge values**: **Deferred to FU-1**. [§3.2.1 «merge entre valores existentes …
  sustituyendo de forma automática dentro de los productos ligados»; HU2.1 "Merge (Fusión)"]
- **FR-023 – Equivalences**: An authorized user MUST be able to turn on, per list, an equivalence column
  and enter an optional equivalence for each value: one free text per value, for mappings to external
  systems, which several values MAY share. Turning the column off MUST hide the texts and keep them
  (OQ-008). Equivalences are not links between values and not per-channel transformations (§3.2.3).
  [§3.2.1 «activar una columna de equivalencias que definir una equivalencia a los valores»; HU2.1
  «para mapeos hacia sistemas externos»]
- **FR-024 – Attribute migration**: **Separate feature, FU-3** (clarification 2026-11-11). [§3.2.1 «Se
  debe poder migrar de un atributo a otro los productos ligados al att/valor, indicando el valor
  equivalente a considerar. Sin eliminar del sistema el atributo»; HU2.1 "Migración entre Atributos"]

**Navigation and interface**

- **FR-025 – Own menu entry**: The feature MUST have its own entry in the side navigation, separate
  from the attribute pages, labelled **"Listas de valores"**, placed right after "Grupos de atributos".
  The interface MUST be in Spanish and use the existing design system components; lists and values
  MUST come from the backend, never be written into the frontend.
- **FR-026 – Feature 004 integration**: Once lists exist, feature 004's LOV attribute creation MUST
  offer the existing lists and accept them, so its "no lists exist yet" refusal no longer applies when
  lists exist. [feature 004 FR-012, DEP-03]

### Observed Existing Behavior

From the reference repository's analysis (tier 2 analysis of tier 3 evidence); not requirements.

- **OEB-001**: P360 stores lists as code–name pairs (`LookupValueRevision` / `LookupValueLang`) and the
  external ID in a separate table (`LookupValueIdentifier`). The product value probably points to the
  value's internal ID (`LookupValueID`), which would make label propagation automatic; not verified.
  [Evidence (as summarized): p360:P360-repositorios/nuevo-pim/docs/arquitectura/pim-headless/modulos/01-plantillas.md:34 (C-05)]
- **OEB-002**: P360 holds about 3,300 lists and about 430 K values, referenced by code.
  [p360:…/pim-headless/modulos/01-plantillas.md:554]
- **OEB-003**: P360 values have an active flag (`IsActive`); a template's list is its filter codes
  intersected with the active values. [p360:…/modulos/01-plantillas.md:526 (R-PLT-06)] Related to
  §3.2.3 "Fuera de alcance", which is out of scope here.
- **OEB-004**: A TO-BE draft in the reference repository puts lists in its own spec
  (`SPEC-PLT-003 Listas de valores`) and leaves equivalences, merge and attribute migration for later.
  [p360:…/modulos/01-plantillas.md:364] Not adopted; noted only as a comparison.

### Conflicts and Open Decisions in Related Documents

Reported per constitution XI; not used as requirements.

- **CF-001 – Selection mode on the list or on the attribute**: §3.2.1 says lists «Pueden ser de
  selección única o selección múltiple»; HU2.1 puts it on the attribute type («Listas de Valores (LOVs):
  Configuración de selección única o selección múltiple»); feature 004 stores it on the attribute. This
  spec keeps feature 004's model (FR-005). (OQ-012)
- **CF-002 – Unlink: "indicate" or "redefine" the type**: §3.2.1 says the other type «debe quedar
  indicado»; HU2.1 says the PIM «exigirá redefinir el nuevo tipo de dato». Feature 004 has no type
  change (its CF-002). Moved to FU-2 with the unlink.
- **CF-003 – What an equivalence is**: §3.2.1 says «definir una equivalencia a los valores»; HU2.1 says
  the column is «para mapeos hacia sistemas externos»; §3.2.3 / HU2.3 "Filtros con transformación"
  define per-channel transformed values («NEGRO INTENSO con ID 0002 … transformación a NEGRO», «columnas
  de transformación asignadas a destinos específicos»). The feature request describes equivalences
  "between LOV values". These are three different readings. Settled 2026-11-11 as HU2.1's reading:
  free text per value (OQ-008, FR-023).
- **CF-004 – Merge maturity**: HU2.1 heads the merge, mapping and migration block "Mecanismos de Fusión
  (Merge-MEJORA)"; §3.2.1 lists merge as a requirement without that label. Merge moved to FU-1.
- **CF-005 – LOV header parameters**: HU2.1 lists list-level "Validation Base Type (ej. Text, Number)",
  "Mask", "Minimum Value / Maximum Value" and "Maximum Length"; §3.2.1 does not. It is not said whether
  they validate value IDs, labels, or both. Not included. (OQ-015)
- **CF-006 – Deletion of used values**: §3.2.1 says deleting a value «generará la eliminación» in the
  records that hold it (removal, after a warning). §3.2.3 "Filtros Generales" offers a softer option:
  marking a value "Fuera de alcance" so historical products keep it. FU-1 follows §3.2.1; the soft
  option belongs to the filters feature.

### Key Entities

- **List of values**: system ID (feature 003, type "lista de valores"), name (unique, ignoring case),
  equivalence column on or off, its values, and the attributes linked to it (read from feature 004).
- **Value**: belongs to one list; one ID (text, unique within the list, entered from an external
  system or generated; OQ-007), label, optional equivalence. Identified by list and ID (FR-012).
- **Link**: an LOV attribute's reference to one list (feature 004's "linked list"); one list, many
  attributes. Read-only in this feature.
- **Change record**: who, when, which deletion, list and values (FR-019).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An authorized user creates a list and adds its first value in under 1 minute.
- **SC-002**: 0 lists ever hold two values with the same ID: 100% of manual additions with an existing
  ID and of files repeating an ID are refused, and bulk rows with an existing ID update that value.
- **SC-003**: A bulk load of 10,000 values is validated and either fully applied or fully reported in
  under 1 minute, and a load with errors applies 0 values.
- **SC-004**: After a label change, the value keeps its ID and the new label is shown everywhere the
  list is consulted, with no manual step.
- **SC-005**: 0 lists linked to an attribute can be deleted, and 0 attributes end up linked to a list
  that does not exist.
- **SC-006**: Once a list exists, an LOV attribute can be created in feature 004 linked to it in under
  1 minute.
- **SC-007**: Users find "Listas de valores" in the side navigation without searching (it is a
  top-level entry).

## Assumptions

- **A-001**: Lists are global, not per template (templates do not exist; §3.2 "Comportamiento Local vs.
  Global" is out of scope).
- **A-002**: List names are unique, ignoring case and surrounding spaces, as for attribute display names
  (feature 004) and group names (feature 005). (OQ-002)
- **A-003**: Value IDs are text: `0001` and `1` are different IDs. Maximum ID and label lengths are set
  in the plan.
- **A-004**: Value IDs are compared ignoring case (`abc` = `ABC`) and surrounding spaces, as for
  feature 003 system IDs. (OQ-006)
- **A-005**: Two values of one list may have the same label; only IDs must be unique. (OQ-011)
- **A-006**: A list linked to any attribute cannot be deleted, as feature 005 refuses deleting a group
  with attributes. (OQ-004)
- **A-007**: Value IDs are unique per list only, so they are not feature 003 system IDs (those are
  unique across all object types).
- **A-008**: Until OQ-009 is answered, the permission is feature 004's `ATTRIBUTE_CREATE`, as feature 005
  did, with the same development stand-in (header `X-Pim-Permissions`, `VITE_DEV_PERMISSIONS`).
- **A-009**: A list may be linked to any LOV attribute; data types other than "Lista de valores" do not
  use lists, so "sharing across data types" means only that one list serves single- and
  multiple-selection attributes (FR-005). If OQ-015 adds a list-level base type, this may change.
- **A-010**: The change record of FR-019 is kept with the data, not sent to an external system
  (constitution IX).
- **A-011**: Generated value IDs follow a per-list sequence; its format is set in the plan.

## Follow-up Features

Recorded so the deferred §3.2.1 rules are not lost. Each needs its own specification.

- **FU-1 – LOV values on products**: needs DEP-03 (products holding LOV values, by list and value ID).
  Delivers label propagation (FR-012), the affected-record count and removal on value deletion
  (FR-013), confirmation with product counts (FR-017), product consistency (FR-018), migration between
  values of one list (FR-021) and merge (FR-022). Carries OQ-010 (partial migration) and CF-004.
- **FU-2 – Unlink a list from an attribute**: delivered with or after attribute editing (DEP-04).
  Delivers FR-015, resolves CF-002, and decides what happens to the values products hold for the
  attribute.
- **FU-3 – Attribute migration**: moving products linked to an attribute/value to another attribute
  with an equivalent value, without deleting the source attribute (FR-024). Needs FU-1. Its value
  mapping is its own: equivalences here are free text for external systems, not links between values
  (FR-023).

- Translations of labels.
